# v1.6.0 engine delivery and latency improvement plan

Status: approved implementation and keep/skip decision record.

Prepared 2026-08-23 against `feat/web-control-panel` at `87964d7`
(`v1.5.0`) for publication as `v1.6.0`. This plan is deliberately evidence-led. It preserves the existing
creative order, including layer-local composition, Temporal, Codec Mosh,
final-program VHS, and blackout. A performance change may not weaken codec
motion identity, transport determinism, freeze/seek semantics, memory
admission, or live/export agreement.

The official implementation decisions are final:

| # | Candidate | v1.6.0 ruling | Reason |
|---:|---|---|---|
| 1 | Separate continuous desire from discontinuity cancellation | **Keep** | Corrected controls rose to 100.00% / 99.94% distinct delivery with zero stale, cancelled, or failed work. |
| 2 | Bounded continuous forward walk | **Keep** | One source period per worker turn prevents a moving target from extending one decode indefinitely while preserving exact discontinuity seeks. |
| 3 | Globally budgeted RGBA decode-ahead | **Skip** | A 64 MiB-per-source prototype still depleted and produced 867/266 ms maxima; reliability would require hundreds of MiB per stream. |
| 4 | Outcome-aware raster/proxy policy | **Keep the measured advice; defer implicit raster reduction** | Intent-qualified holds distinguish healthy corrected MP4s from bursty VP9. Native decode stays exact and proxy creation remains explicit. |
| 5 | Global multi-layer CPU coordinator | **Skip; keep bounded VP9 slice threading** | No coordinator benefit is established for the evidence workload. Four VP9 slice threads reach the measured bounded throughput plateau without central scheduling complexity. |
| 6 | Promote D3D11VA | **Skip / retain probe only** | Downloaded hardware measured 1.726 ms versus 0.500 ms software on the existing fixture, with no zero-copy or motion-semantic proof. |
| 7 | Rational deadline pacing | **Keep** | Exact 30 Hz deadlines, truthful lateness/skipped counts, and `WaitUntil` remove drift, false misses, and redraw spin. |

The independent egui raw-view correction is also kept strictly as a
color-correctness repair. The complete final media receipt is
[`docs/evidence/v1.6.0-decoder-delivery-receipt.md`](evidence/v1.6.0-decoder-delivery-receipt.md).

## Decision summary

The corrected 720p experiment is not GPU-, upload-, RAM-, or VRAM-bound. Its
persistent visible freezes are principally decoder-delivery starvation:
continuous 30 Hz source selections advance the decoder command epoch, and a
new epoch invalidates work already underway. Successful decode percentiles
therefore describe only the small set of attempts that survive cancellation.

The causal chain in the current tree is:

```text
30 Hz transport tick
  -> sample_due selection
  -> command epoch increments
  -> in-flight decode fails is_current(epoch)
  -> attempt counted as a frame drop but omitted from decode-duration p95
  -> no new source image is published/uploaded
  -> renderer and swapchain continue presenting the previous image
  -> operator sees a freeze despite healthy render/GPU timing
```

The first work must remove that wasted serial work, in accordance with
Amdahl's Law. Only after that bottleneck is removed should the engine spend
complexity or memory on lookahead, wider CPU scheduling, or hardware decode.
Gustafson-style scaling applies later to additional simultaneously visible
layers; it cannot rescue one layer that repeatedly cancels its own work.

Operational rulings:

- Do **not** raise RAM or VRAM caps as a remedy. The observed allocation was
  156,672,000 / 855,072,768 GPU bytes (18.3%) and 5,529,600 / 49,766,400 Mosh
  send bytes (11.1%). PresentMon measured GPU-active p95 at 4.674 ms against a
  33.333 ms program period.
- Do **not** prescribe proxies as the primary engine fix or for the corrected
  720p controls. After the scheduler repair those files pass at 100.00% and
  99.94% distinct delivery. Do recommend an operator-authorized proxy for the
  exact 1080p VP9 sources, whose final intent-qualified hold maxima are 466 ms
  and 233 ms.
- Preserve bounded newest-intent behavior. None of the work below permits an
  unbounded frame queue or blocks the render thread.
- Treat the `egui_wgpu` sRGB warning as a separate color-correctness item. It
  is not evidence of decoder, render, or presentation inefficiency.

### HUD recording

Evidence file: `2026-08-23 18-48-04.mp4`, 7,861,107 bytes,
SHA-256 `6a1fb047ef792a73c6ae0a2f1e102f5218ba30697394623500ba1d9077b860ca`.

miss and must not be used as a release KPI in its current form.

freezes. The central white bloom is the phone flash and is excluded from all
production-image findings. The MOV was available for metadata inspection
(1920x1080, nominal 60 fps, 120.87 s) but was no longer present when the
frame-difference pass began, so this plan does not invent an exact visual-hold
count from it. Decoder ages and the operator observation are sufficient to
open the scheduling work; a later retained copy can strengthen, but need not
block, the A/B receipt.

## Gate 0 — make the measurements truthful

This is a prerequisite and is not counted among the seven performance
improvements. It should land first because every later keep/kill decision
depends on it.

### Required telemetry changes

- Replace `last_frame_time = now` accounting with an exact rational schedule
  origin and tick ordinal. For 30 fps, deadline `n` is
  `origin + floor(n * 1_000_000_000 / 30) ns`; no permanently truncated
  microsecond period is the authority.
- Report positive schedule lateness p50/p95/p99, skipped program ticks, and
  longest late streak. A skipped tick means at least one whole scheduled
  period was crossed, not that a frame finished a few microseconds after its
  ideal timestamp.
- Expose transport facts separately: `sample_due`, authored `held`, distinct
  due source identities, discontinuities, and loop/cue/seek generations.
- Split decoder loss into queued-intent overwrites, continuous coalesces,
  discontinuity cancellations, in-flight supersessions, stale-generation
  completions, completed-mailbox overwrites, and upload failures. Do not sum
  these into one unlabeled `drops` value.
- Record duration and decoded packet/frame work for **every** attempt,
  including superseded work. Retain a separate successful-decode percentile.
- Add time since last accepted GPU upload, same-generation source-hold
  p50/p95/p99/max, target lag at publication, and accepted distinct source
  identities. Publish-to-consume age alone has survivor bias.
- Keep fixed-size windows (the existing 64/512-sample precedents are
  suitable), cumulative totals, a measurement epoch, and an explicit reset.
  Warm telemetry must allocate nothing and take no decoder/render mutex for
  longer than the existing bounded snapshot operations.
- Keep PresentMon as the external display authority. The engine must not
  relabel successful submission as successful physical display.

### Gate 0 tests

- A rational 30 fps fixture produces exactly 30 scheduled ticks per second
  without systematic misses.
- A 7 us overrun records 7 us of lateness and zero skipped ticks.
- A 100 ms stall records the exact skipped-tick count and late streak.
- Superseded work contributes to all-attempt duration/work counters but not
  to successful-decode percentiles.
- An authored transport hold is distinguishable from a decoder delivery hold.
- Snapshot serialization remains bounded and backwards-compatible through
  additive/defaulted fields.

## The seven performance improvements

### 1. Separate continuous desire from discontinuity cancellation

**Priority: immediate; highest expected value.**

**Outcome: kept.** Same-generation work now completes under the source
generation cancellation token; the one-slot desire remains bounded.

Current anchors:

- `src/layers/mod.rs::apply_transport_tick_with_overrides`
- `src/video/threaded.rs::DecodeCommandMailbox::select_after_with_kind`
- `src/video/threaded.rs::run_decode_commands`

Every accepted `Select` currently advances `current_epoch`; the worker tests
that epoch before, during, and after decode. A normal next-frame request thus
cancels a same-generation decode that is already close to completion.

Implementation:

1. Retain `FrameSelection::generation` as the discontinuity token. Seek, cue,
   loop/reflection, source replacement, stop, and direction-law changes cancel
   older work immediately.
2. Add a monotonically increasing intent sequence for observability and
   freshness, but do not use a same-generation continuous sequence change as
   a cancellation predicate.
3. Keep exactly one running decode and one overwriteable desired intent per
   decoder. A continuous update replaces only the desired intent; no backlog
   can form.
4. Permit a completion from the current generation to publish even when a
   newer continuous intent exists. The worker then takes the newest desired
   target, never each intermediate target.
5. Bound stale publication: if a completion trails the newest desired source
   time by more than two source periods, preserve its decoder state but skip
   audience publication and immediately continue toward the latest target.
   Record this as a continuous coalesce, not a discontinuity drop.
6. Preserve the existing rule that upload success, not mailbox consumption,
   commits the codec-motion predecessor.

Correctness tests must cover forward playback, reverse playback, pause,
Media Freeze, Program Freeze, scrub bursts, cues, loop boundaries, source
replacement, Stop, and failure/panic paths. A stale generation may never
publish; a merely older same-generation sequence may never poison motion
identity.

Keep criterion: on the corrected two-source patch after warm-up, at least 95%
of distinct due source identities must reach an accepted upload, source-hold
p99 must be no more than two program periods, and no same-generation hold may
exceed four program periods during the 60-second receipt.

### 2. Retarget the existing forward walk without chasing forever

**Priority: immediately after improvement 1.**

**Outcome: kept in its bounded form.** Continuous live walks yield after one
newly due source period; prepared seeds, seeks, and discontinuities remain
exact.

Current anchor: `src/video/decoder.rs::seek_decode_after_interruptible` and
`can_continue_forward`. The engine already has a valuable forward-decode fast
path; this plan does not replace it with another seek loop.

Implementation:

1. Let the worker expose the latest same-generation desired target at safe
   packet/frame boundaries.
2. During a monotonic walk, raise a forward target (or lower a reverse target)
   without seeking or flushing the decoder. A direction reversal or
   discontinuity returns the typed superseded result immediately.
3. Check for a newer target before expensive RGBA materialization. Intermediate
   native decoder frames should advance codec state without becoming packed
   mailbox images.
4. Bound retargeting by both source span and wall time. One invocation may
   follow at most two newly due source periods before it must publish the best
   eligible frame or yield to the scheduler. This prevents an always-moving
   target from starving publication.
5. Carry the exact skipped codec-motion transition chain from the last
   accepted identity to the selected destination. If adjacency cannot be
   proven, publish correct pixels with motion unavailable, never fabricated
   vectors.

Keep criterion: compared with improvement 1 alone, abandoned decoded-frame
work must fall by at least 50% or accepted-upload hold p99 must improve by at
least 20%, with identical selected frame identities and codec-motion products
on deterministic fixtures. Otherwise fold the safe parts into improvement 1
and do not retain extra retargeting complexity.

### 3. Add an optional, globally budgeted decode-ahead buffer

**Priority: conditional on residual jitter after improvements 1 and 2.**

**Outcome: skipped and prototype removed.** A 64 MiB-per-source implementation
depleted during the full VP9 run and worsened the Swan maximum hold to 867 ms.
The release restores the 32 MiB reverse-cache bound and carries no forward
RGBA queue.

This is not an unconditional per-layer history ring. It is a process-wide,
byte-admitted ready-frame budget that may grant zero, one, or two future
frames to a decoder and falls back exactly to newest-intent playback when the
budget is unavailable.

Implementation:

1. Predict only deterministic continuous selections from the evaluated
   transport law. Do not predict through a seek, cue, source replacement,
   direction change, loop/reflection boundary, or non-finite/modulated
   discontinuity.
2. Preallocate a small `ReadyFrame` ring at source activation. No growth or
   allocation occurs on the frame path.
3. Charge every RGBA image and codec-motion product to the active media ledger
   and expose active-source bytes in Stage Health. The current `media 0/...`
   prepared-cache number is not sufficient accounting for this feature.
4. Select the exact identity due for the current transport tick; discard
   obsolete identities without calling them decoder failures.
5. Flush by generation and wake direct current-time decode on interaction, so
   lookahead adds throughput slack but no control latency.

At 1280x720, one RGBA8 frame is 3,686,400 bytes. Two additional frames for
each of the two evidence sources would cost 14,745,600 bytes before codec
products and alignment. The plan must admit the checked total, not infer that
the existing cap makes it harmless.

Keep criterion: implement only if improvements 1 and 2 still leave
same-generation source-hold p99 above two periods. Retain only if the buffer
halves those residual holds without increasing interaction-to-new-image p95
by more than one program period or violating the warm-allocation invariant.

### 4. Make decode resolution and proxy advice outcome-aware

**Priority: high for 1080p/4K sources, after the scheduler is honest.**

**Outcome: measured advice kept; implicit raster reduction deferred.** Proxy
assessment excludes scheduler cancellations, requires sustained historical
loss, and consumes intent-qualified delivery-hold p95/peak. Native raster
decoding remains exact; the existing content-addressed proxy path remains the
explicit performance/quality choice.

Implementation:

1. Introduce an immutable, admitted `DecodeRasterPlan` at source activation:
   source dimensions, requested raster dimensions, scaler/color path, exact
   byte cost, and quality mode.
2. Preserve native-source decoding as the exact default. Offer an explicit
   output-bounded performance mode that converts directly from codec format to
   the admitted layer/output raster in one swscale operation, avoiding a
   full-resolution RGBA intermediate. A transform that can reveal additional
   source detail must select native mode or state the quality tradeoff.
3. Keep generated proxies content-addressed and operator-authorized. Do not
   silently transcode merely because a cumulative counter once increased.
4. Replace `assess_proxy`'s `dropped_frames != 0` rule with sustained windowed
   evidence after scheduler-caused coalesces are excluded: delivery shortfall,
   accepted-upload hold, successful/all-attempt decode cost, and visible-layer
   pressure. Require consecutive bad windows and add hysteresis before the HUD
   changes recommendation.
5. Report the reason and window: for example, `decode p95 over budget in 3/3
   windows`, rather than the generic historical `frame drops` reason.
6. Re-run the original WebM, 1080p H.264, corrected 720p H.264, and generated
   proxy under identical patch timing. Record source identity, decode raster,
   frame identities, hold percentiles, and quality mode.

Keep criterion: retain output-bounded decoding only if 1080p-to-720p
all-attempt decode p95 improves at least 25% and its declared quality fixture
passes. Keep revised proxy advice if it recommends the corrected 720p files
only when delivery remains bad after improvements 1 and 2, and clears after
healthy windows. Native exact mode must remain unchanged.

### 5. Bound and schedule multi-layer CPU decode work

**Priority: conditional scaling work; Gustafson tranche.**

**Outcome: central coordinator skipped; bounded VP9 threading kept.** Local
slice-thread measurements plateaued at four workers. The evidence does not
justify imposing a process-wide coordinator on the healthy one/two-source
path; one remains a future four/eight-layer benchmark candidate.

One source already owns one decoder worker, while FFmpeg may create internal
codec threads. With many visible layers, unconstrained multiplication can
oversubscribe CPUs even though each layer's mailbox is bounded.

Implementation:

1. Measure process logical cores, per-decoder busy time, runnable wait, and
   FFmpeg thread configuration. Do not choose a worker count from core count
   alone.
2. Add a process-wide decode admission coordinator with a fixed job bound and
   earliest-deadline-first ordering. Decoder state remains single-owner; the
   render thread only publishes intent and never waits for admission.
3. Reserve one latency lane for discontinuities/current-frame recovery so
   lookahead or inactive preparation cannot delay an operator seek or cut.
4. Bound FFmpeg threads per active decoder so `visible layers × codec threads`
   remains within the measured CPU budget. Reconfiguration occurs only on
   source/visibility topology boundaries, not every frame.
5. Avoid synchronized bursts: when deadlines are equivalent, rotate the first
   admitted layer deterministically by program tick rather than permanently
   favoring layer order.

Benchmark one, two, four, and eight visible video layers, plus one source
alone from each evidence file. Keep criterion: at four and eight layers the
coordinator must reduce p95 runnable/decode lateness or accepted-upload holds
by at least 20%, while one- and two-layer p95 may not regress by more than 5%.
If the post-improvement-2 scaling curve is already healthy, do not land a
central coordinator.

### 6. Promote hardware decode only behind semantic and performance gates

**Priority: optional acceleration after software scheduling is repaired.**

**Outcome: skipped for live playback.** D3D11VA remains a probe-only backend;
software decode is the v1.6.0 authority.

The existing D3D11VA backend is evaluation-only. Its tracked 640x360 receipt
proved 72/72 byte-exact decoded frames, but hardware download measured about
1.726 ms/frame versus 0.500 ms/frame for software on that fixture. It carries
no live-path performance proof and no zero-copy implementation.

Implementation sequence:

1. Benchmark downloaded D3D11VA against repaired software decoding on both
   corrected 720p clips, the 1080p H.264 clips, long-GOP material, and at least
   one unsupported/fallback codec. Include all-attempt and accepted-upload
   timing, not only decode-library wall time.
2. Establish feature eligibility. A layer requiring FFmpeg exported motion
   vectors for Codec Mosh stays on software unless hardware frames prove the
   same exact motion products. Never run a hidden second software decoder for
   motion while claiming hardware efficiency.
3. If downloaded hardware wins, add an opt-in live backend with typed fallback
   to software, generation-safe cancellation, matching telemetry, and no
   export-path change.
4. Treat D3D11 texture sharing into wgpu, adapter matching, GPU YUV conversion,
   and true zero-copy as a separate subtranche with its own resource ledger and
   interop receipt. `hardware_decode_active` and `zero_copy_active` become true
   only from runtime proof.
5. Fail closed: device removal, remote sessions, unsupported formats, missing
   motion products, or adapter mismatch must restore software without changing
   transport identity.

Keep criterion: do not promote the evaluation backend unless live full-size
delivery p95 or CPU consumption improves at least 20% with no new holds,
pixel/identity disagreement, motion-semantic loss, or render-thread wait. If
downloaded hardware loses, retain the probe-only backend and skip live usage;
that is a successful evidence-based decision.

### 7. Use rational deadline pacing and preserve healthy presentation modes

**Priority: independent correctness/latency cleanup after Gate 0.**

**Outcome: kept.** The event loop uses rational deadlines and `WaitUntil`, and
Stage Health reports lateness and whole skipped ticks separately.

Implementation:

1. Drive the next deadline from an origin and tick ordinal, not
   `last_frame_time = now`. This prevents accumulated drift.
2. When late by whole periods, advance to the newest due ordinal and record the
   skipped count; do not render a burst of stale catch-up frames.
3. Use the event loop's deadline wake mechanism where supported, while input,
   decoder completion, surface recovery, and control events can still wake it
   immediately. No blocking sleep belongs in the render callback.
4. Keep `Fifo` and `desired_maximum_frame_latency = 2` as the control baseline.
   Test latency 1 only as an A/B; retain it only if PresentMon and interaction
   latency improve without new display gaps.
5. Treat the first compositor-mode interval as warm-up evidence, not as steady
   state. Preserve the already healthy Independent Flip behavior: the supplied
   trace had zero drops in 1,509 steady-state presents.
6. Expose separate preview/output/StageMap presentation identities in receipts
   so multiple swapchains cannot be conflated.

Keep criterion: after warm-up, PresentMon must show zero dropped presents over
60 seconds on the corrected patch, `msBetweenPresents` p99 no worse than the
35.043 ms evidence baseline by more than 5%, no gap above two program periods,
and lower or equal idle CPU use. Decoder source-hold criteria remain separate.

## Separate color-correctness item — egui framebuffer format

Warning:

```text
egui_wgpu::renderer: Detected a linear (sRGBA aware) framebuffer
Rgba8UnormSrgb. egui prefers Rgba8Unorm or Bgra8Unorm
```

Materiality: renderer hygiene and color-space clarity for the native egui
preview, not demonstrated efficiency. No decode, hold, PresentMon, or latency
improvement may be claimed from removing it.

Planned correction:

1. Derive the raw twin of the selected main sRGB surface format with
   `remove_srgb_suffix()`.
2. Advertise that compatible raw format in the main surface configuration's
   `view_formats` when it differs from the surface format.
3. Construct `egui_wgpu::Renderer` for the raw target format and create the
   acquired main-surface view with that raw format for the egui pass.
4. Keep the audience composite, output-window blit, and StageMap presentation
   sRGB contracts unchanged. The existing raw `output_view` used as egui's
   registered program texture remains a separate sampling concern.
5. Add helper tests for sRGB/raw format pairing and a physical-GPU preview
   capture comparing reference color patches before and after. Confirm the
   warning is absent on startup.

Acceptance is color evidence plus warning removal. Performance values are
recorded only to prove no regression, not to manufacture a speedup claim.

## Common benchmark and receipt matrix

This matrix governed candidate evaluation. A row belonging only to a skipped
candidate is closed by its explicit skip receipt; it is not a demand to ship
that candidate or a blocker requiring speculative implementation. The final
release runs the applicable corrected-H.264 and VP9 two-source receipts plus
the complete deterministic test/lint matrix.

Every numbered improvement receives an A/B receipt against its immediate
parent commit. Use a fresh process, wait ten seconds for startup and
Independent Flip, reset telemetry, then measure 60 seconds without control
input.

Required workloads:

1. Corrected two-source 1280x720/30 H.264 Cygnus patch.
2. Equivalent two-source 1920x1080 H.264 patch.
3. Equivalent VP9 WebM patch.
4. Swan-only and Nature-only isolation runs.
5. Codec Mosh off, then armed with motion wakes, to prove motion semantics.
6. A discontinuity script covering seek, cue, reverse, loop, pause, Media
   Freeze, Program Freeze, and source replacement.
7. One/two/four/eight visible-layer scaling fixtures for improvements 5 and 6.

Each receipt records:

- exact commit, dirty-tree state, OS, CPU, adapter, driver, FFmpeg version;
- content identity, codec, dimensions, nominal/source timing, proxy key and
  decode raster mode;
- requested/distinct-due/coalesced/cancelled/completed/published/consumed/
  accepted-upload counts by reason;
- successful and all-attempt decode/work percentiles;
- source-hold, accepted-upload age, target lag, upload, frame-schedule, GPU,
  Present API, and display-change percentiles;
- maximum queue depth and every admitted CPU/GPU/media byte;
- PresentMon CSV, Stage Health snapshots, and external 60/120 fps audience
  recording with hashes;
- deterministic frame-identity and codec-motion comparison results.

No tranche may call a lower publication count a latency win, hide discarded
work outside percentiles, or compare runs with different warm-up/reset
boundaries.

## Landing order and stop points

1. Gate 0 telemetry and benchmark harness.
2. Improvement 1; remeasure all three media families.
3. Improvement 2; retain only if its keep criterion is met.
4. Decision checkpoint: if corrected 720p holds are closed, improvement 3 is
   skipped and recorded as unnecessary.
5. Improvement 4 and its proxy-advice migration.
6. Improvement 5 only if the post-fix scaling curve warrants it.
7. Improvement 6 only if downloaded/live hardware passes its gates; zero-copy
   remains a separate decision.
8. Improvement 7 and the independent egui color item, each with separate
   materiality claims.

The retained changes land as one reviewable v1.6.0 release branch because the
telemetry, scheduler, pacer, and advice laws form one tested delivery seam.
Each candidate still has an explicit keep/skip result and rollback boundary.
A failed keep criterion closes that candidate without merging speculative
complexity.
