## Independent-verifier timezone finding

The fresh verifier also exposed a portability defect after publication. The
published source ZIP has SHA-256
`d039a88267ac2f85d4c8cbbe8d69cdb844affcf79d3377719baacb0b09c31c27`.
It reproduces exactly on the UTC GitHub runner and when the independent desktop
sets `TZ=UTC`.

On the same commit, prefix, Git version, and source tree, an unqualified
`git archive --format=zip` on the `America/New_York` desktop instead produced
SHA-256 `0522988a43c9615c89fa548fe5fe3faf53e6105490c7754c1fbce8aec69b861e`.
ZIP stores a DOS timestamp without timezone metadata; Git derived that field
from the caller timezone. The file names, source bytes, ordering, and commit
were unchanged, but the archive container bytes differed. Consequently,
`verify-release.py verify` could reject a sound published release merely
because an independent verifier was outside UTC.

This was not an asset-integrity or signing failure. Explicit UTC regeneration
matched the published archive exactly, after which the complete verifier,
both Sigstore checks, and all eleven GitHub attestation checks passed.

## Timezone-independent correction

`create_source_archive` now copies the caller environment, sets `TZ=UTC` only
for the `git archive` child process, and leaves the caller's process environment
unchanged. The same function is used when preparing a release and when
reproducing a downloaded source archive, so producer and verifier now share an
explicit timezone contract on Windows, Linux, and macOS.

The release verifier self-test sets two hostile caller zones,
`America/New_York` and `Pacific/Honolulu`, creates the same archive in each,
proves the caller's `TZ` value was not mutated, and requires byte-identical
SHA-256 results. Removing the child-process UTC normalization makes the test
fail on timezone-sensitive Git implementations.
