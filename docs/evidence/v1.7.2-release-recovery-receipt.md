## Checkout-boundary correction

The failed workflow used `source-a` both for mutable dependency-policy tooling
and as claimed clean build input A. The recovery removes that overlap:

1. dependency fetch, vendor verification, advisory checks, license checks, and
   dependency-evidence generation run only in a dedicated `policy-source`
   checkout of the verified candidate commit;
2. independent source A and source B are checked out only after all mutable
   policy tooling has completed;
3. immediately before reproducibility preparation, both build checkouts are
   checked under the same sterile Git configuration as the canonical wrapper;
4. the preflight requires each checkout to resolve to the verified commit and
   to have zero staged, tracked, or untracked status rows; and
5. any refusal identifies the exact checkout and emits a bounded JSON sample
   of status rows instead of discarding the only diagnostic witness.

The canonical build wrapper remains fail-closed. No cleanup, reset, ignored-file
exception, or dirty-source fallback is introduced.

The repository also makes LF checkout ownership explicit for `.gitignore`,
`*.tldr`, and `*.dict`, closing uncovered Git-for-Windows normalization paths.
`fuzz/corpus/**` remains opaque binary data through an explicit `-text` rule.
This addresses a concrete dirty-checkout mechanism without claiming that the
unlogged `v1.7.1` status row is known.

## Pre-tag Release trust qualification

`workflow_dispatch` now qualifies only the exact remote default-branch head,
while `release_tag` remains the planned version identity. Dispatch mode
requires the selected event SHA, checked-out commit, and remote default head to
agree, requires the planned tag to equal the Cargo package version, and refuses
an existing remote tag or GitHub release. It executes the exact workflow gate,
policy checks, fresh-checkout preflight, two unequal-root builds, byte
comparison, SBOM generation, deterministic package/provenance assembly,
unsigned package verification, and pinned cosign installation. A final
read-only check requires the remote default head to remain exact and the tag
and release to remain absent. Signing, attestation, workflow artifact upload,
draft creation, release upload, publication, and redownload are skipped in
dispatch mode and remain restricted to an actual `v*` tag-push event.

The tag-push and dispatch paths are mutually exclusive Windows jobs that share
one YAML-anchored step sequence. Dispatch receives only `contents: read` and
`attestations: read`, with no identity-token or write permission. The tag-push
job alone receives the publication and OIDC authority required by its guarded
signing and release steps.

This permits the Windows-hosted release path to earn evidence before another
immutable version tag is minted. A dispatch result is qualification evidence
only; it cannot substitute for the later tag-push Release trust run or for
independent public-release verification.
