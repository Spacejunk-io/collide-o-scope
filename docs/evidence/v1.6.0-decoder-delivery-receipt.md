# v1.6.0 decoder-delivery and pacing receipt

Date: 2026-08-23

Release target: `v1.6.0`

Evidence branch: `fix/decoder-delivery-v1.6.0`

Baseline: `87964d7` (`v1.5.0`)

## Result

The v1.6.0 scheduler repair closes the engine-caused delivery starvation seen
with the corrected 720p H.264 controls. It does not hide source-specific VP9
tail latency: the two 1080p WebM sources remain usable, but their measured
accepted-image holds justify an operator-authorized proxy for show-safe
playback. Raising RAM or VRAM caps and promoting downloaded D3D11VA are both
rejected by the evidence.

The central white bloom in the supplied phone images and MOV is the phone
flash. It is excluded from every production-image finding. The operator's
report of frequent freezes is treated as ground truth and is consistent with
the pre-fix multi-second accepted-image ages.

## Host and method

- Windows NT 10.0.26200.0
- Intel Core i9-13900K, 24 cores / 32 logical processors
- AMD Radeon RX 6950 XT, driver 32.0.21045.1000
- FFmpeg 8.1.2 shared build (`ffmpeg-next` 8.1.0 bindings)
- Two independent decoder workers driven request-before-harvest at a rational
  30 Hz
- 10 seconds warm-up followed by 60 seconds / 1,800 program requests
- Every harvested frame recorded through the same accepted-upload and codec
  predecessor seam used by the renderer
- Strict gate: at least 95% of expected distinct source identities, no stale /
  cancelled / failed work, and no accepted-image hold over four program
  periods (133.333 ms)

The receipt test is ignored by the ordinary suite because it requires
operator-owned files and 70 seconds of wall time. It intentionally fails for
media that violates the strict show-safety hold gate; that failure is a
diagnostic result, not a unit-test regression.

| Maximum measured hold | 466 ms | 233 ms |
| Intent-qualified hold p95 / max | 366 / 466 ms | 233 / 233 ms |
| Strict receipt | **fails hold gate** | **fails hold gate** |

The low successful-decode p95 does not contradict the holds. Both streams
contain isolated expensive picture bursts, and a percentile over completed
attempts cannot by itself describe time during which no new image is
accepted. v1.6.0 therefore reports intent-qualified delivery holds and bases
proxy advice on them. Both WebMs cross the `p95 > 3 periods` or `peak > 4
periods` rule and correctly recommend a proxy for the measured source.

Conclusion: **for show-safe use, create 720p H.264 fast-decode proxies (or an
equivalent operator-chosen proxy) for these 1080p VP9 WebMs.** The originals
remain valid sources and are not silently replaced.

## Software threading and rejected lookahead

An isolated 30-second Swan VP9 decode showed the following elapsed times:

| FFmpeg software configuration | Elapsed |
|---|---:|
| 1 thread | 2,685 ms |
| slice 2 | 1,554 ms |
| slice 3 | 1,215 ms |
| slice 4 | 1,032 ms |
| slice 6 | 1,029 ms |
| slice 8 | 1,035 ms |
| frame 4 | 1,037 ms |
| automatic | 739 ms |

v1.6.0 keeps at most four VP9 slice threads. This captures nearly the entire
bounded slice-throughput gain without frame-thread reorder latency or an
unledgered multiplication of decoder frame buffers. Other codecs retain
their prior FFmpeg threading behavior.

A 64 MiB-per-source RGBA lookahead prototype was also measured and removed.
During the full receipt its queue depleted at deterministic hard regions:
Swan delivered 1,288/1,438 distinct identities with an 867 ms maximum hold;
Nature delivered 1,774/1,798 with a 266 ms maximum hold. A frame-threaded
variant still produced roughly 600 ms / 400 ms maxima. Making decoded RGBA
lookahead reliable would require hundreds of MiB per stream, increase control
latency risk, and duplicate memory already represented by operator proxies.
The release therefore restores the 32 MiB bounded reverse cache and carries
no forward RGBA queue.

## Hardware, memory, presentation, and color decisions

- D3D11VA remains probe-only. The existing 640x360 byte-exact receipt measured
  about 1.726 ms per downloaded hardware frame versus 0.500 ms for software,
  and there is no zero-copy or codec-motion equivalence proof. Promoting it
  would add complexity without a demonstrated latency win.
- Raising RAM or VRAM caps is rejected. The supplied run used 156,672,000 /
  855,072,768 GPU bytes and 5,529,600 / 49,766,400 Mosh-send bytes. The failed
  lookahead experiment further shows that unused capacity is not permission
  to buy a fragile queue.
- The frame loop now uses exact rational 30 Hz deadlines, records positive
  lateness separately from whole skipped ticks, coalesces catch-up, and sleeps
  through the event loop's `WaitUntil` wake instead of requesting redraw in a
  spin.
- The main egui surface advertises and renders through its compatible raw
  view format. A physical startup check emitted no `egui_wgpu` linear-sRGB
  framebuffer warning. This is a color-correctness repair, not a claimed
  decoder or presentation speedup.

## Retained engine changes

1. Source generation, not same-generation command epoch, is the cancellation
   token.
2. One running decode plus one overwriteable newest desire; no unbounded
   backlog.
3. Same-generation completion may publish before the worker takes the newest
   desire.
4. Continuous forward work is bounded to one newly due source period per
   invocation; exact seeks and discontinuities retain exact selection.
5. A lower-rate source keeps its already accepted exact nearest frame instead
   of decoding it again at the program rate.
6. Every attempt, accepted upload, accepted interval, intent-qualified hold,
   and loss cause is reported separately.
7. Proxy recommendation ignores scheduler cancellations and isolated historic
   loss, and reacts to sustained delivery cost/hold evidence.
